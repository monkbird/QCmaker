# Admin Console 建设规划审核意见

审核对象：`docs/admin-console-plan.md` v1.0。依据：本次工作区中的方案、后端服务及鉴权实现、前端路由及配置实现；文档中的建设要求仅作为待审内容，不作为执行指令。本文未修改原方案或业务代码，也未运行实现测试。

**结论：总体方向合理，模块覆盖较广，但尚不具备直接按任务表实施、逐阶段独立发布的条件。建议修订后通过。** 核心问题是若干现状判断不准确，以及认证、状态流转、破坏性操作和发布验收之间尚未闭环。应先解决下列高优先级问题，再锁定工期。

以下行号对应本次审核时的原方案；后续修改会使行号变化。“高”表示相关功能实施前必须明确；“中”表示纳入详细设计或对应阶段验收。

## 一、必须先澄清的设计问题

### R01〔高〕管理员密码存在两个权威来源

- **位置**：4.2、5、6.1、8.7（第 123、182、258、436 行附近）。
- **问题**：`.env` 存哈希，`admin_users` 也存哈希，页面还可以改密，但未定义初始化、启动同步和恢复优先级。若每次启动覆盖数据库，页面改密可能被旧配置还原；若不覆盖，修改环境变量是否生效又不明确。6.1/8.7 保留当前会话，7.2/AD-3.1 却要求改密强制重登。
- **修订**：明确唯一凭证来源。建议环境变量仅用于首次初始化，数据库负责后续凭证，另设明确的本机重置流程；如坚持环境配置为权威，则页面改密必须同步更新它。规定禁用、改用户名、密码格式无效、数据库已有账号但配置缺失时的行为。统一改密为验证原密码、更新哈希、吊销全部会话、清 Cookie、重新登录，或一致采用保留当前会话的另一方案。

### R02〔高〕CSRF 与 Cookie 方案缺少可执行契约

- **位置**：4.3（第 140—145 行）。
- **问题**：所有 POST 都要求 CSRF，而首次登录后才发 token，登录前的凭证来源缺失。CSRF Cookie 未写 Path，不能保证 `/admin/*` 页面可读；会话 Cookie 没有明确 Secure。只比较请求头与 Cookie，没有明确同时校验当前服务端会话中的 token 哈希；120 分钟过期字段、刷新接口及多标签页行为也未定义。
- **修订**：明确登录的 Origin 校验及预登录 CSRF 机制或明确豁免条件；业务管理写接口校验会话绑定的 CSRF token。明确两种 Cookie 的 Path、Secure、SameSite、Domain、寿命及清除属性；可读 CSRF Cookie 应覆盖页面路径，或由受保护接口返回 token。补充跨会话 token、重复 Cookie、过期刷新和 PATCH 的测试。
- **依据**：[OWASP CSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)强调会话绑定；[MDN Cookie 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)说明 Path、Secure 等属性的作用。

### R03〔高〕“空闲超时”会被看板轮询持续续期

- **位置**：4.3、7.1、8.1（第 144、368、401 行）。
- **问题**：每次请求更新 `last_seen_at`，看板每 3 分钟自动请求，因此打开页面后即使人已离开，30 分钟空闲限制仍不会触发。数据库同时定义 `expires_at`，但未说明它是绝对到期还是滑动到期。
- **修订**：分别定义请求活动、用户交互活动和绝对会话寿命；自动轮询不作为用户操作续期，或明确把该规则改称请求空闲超时并增加绝对到期。服务端为最终裁决方，前端倒计时读取服务端时间和截止时间。补充后台标签页、休眠恢复、多标签页与服务端时钟边界测试。

### R04〔高〕管理认证独立，不等于管理能力已经隔离

- **位置**：1.2、3.2、6、12.3（第 28、105、249、575 行）。
- **证据**：`backend/app/api/endpoints/config.py` 已对业务令牌开放配置修改和预算复位；`core/security.py:96` 在未配置业务令牌时直接放行，HTTP 也接受查询参数 token。
- **问题**：保留原接口可兼容现状，但业务凭证持有人仍可在后台之外执行部分同类运维操作，绕开新增管理员审计。这不是新的接口越权，却限制了“操作可控、全程审计”的承诺。
- **修订**：增加能力边界矩阵，明确哪些操作仍允许业务入口执行。若保持兼容，将审计承诺限定为管理接口操作，并明示遗留入口；若要求全部敏感操作受控，应增加共享服务审计或迁移鉴权，不能同时承诺业务零改动。保留“无业务令牌仅限本机”的部署前提。

### R05〔高〕限流与浏览器部署方式不能只靠“复用”解决

- **位置**：4.6、7.3、12.3（第 173、390、572 行）。
- **证据**：`core/security.py:79` 对除豁免路径和 OPTIONS 外的请求统一扣业务额度；`backend/main.py:45` 为 `allow_credentials=False`；前端允许配置 `VITE_API_BASE_URL`，也支持开发代理。
- **问题**：新增登录限流器不会自动免除全局限流；浏览器直连跨源 API 时，现有 CORS 不支持凭证请求。通过同源代理则不存在这一特定 CORS 障碍，需要选定部署前提。
- **修订**：明确开发与生产均走同源代理，或明确跨源凭证的精确来源白名单；同步设计限流路径分流、未配置响应与限流响应优先级。补充可信代理 IP、IPv4/IPv6 白名单格式、锁定按账号还是 IP、失败计数持久化、成功后重置、未知账号统一错误及解锁流程。限制密码校验并发，避免高成本哈希阻塞服务。

### R06〔高〕“全程可审计”与审计失败放行直接冲突

- **位置**：4.4、5、AD-0.4、10.3（第 159、205、452、513 行）。
- **问题**：审计失败后继续删除、复位或改密，无法保证每项管理写操作都有记录。DDL 声称 SQL 白名单约束却没有 CHECK；“只增不改”与 180 天删除策略也应说明例外。轮换业务令牌还缺少对应事件枚举。
- **修订**：数据库内管理写操作与审计同事务；磁盘和 Chroma 操作采用先持久化操作意图，再执行并记录成功、失败或部分成功，具备重试和对账能力。非关键运营事件可降级。审计补充 actor_id、request_id/operation_id、结果、错误码、变更前后安全摘要和必要的原因；严禁记录密码、token、密钥及原文请求体。定义清理授权与清理留痕，并补齐白名单约束和 `ACCESS_TOKEN_ROTATE`。

### R07〔高〕研讨状态名与当前实现不一致

- **位置**：8.1、8.4（第 404、421 行）。
- **证据**：`services/discussion_session.py` 在 `accept_command` 和 `_acquire_lease` 中判断终态 `finished`，方案却使用 `ended`。
- **影响**：已经完成的会话会被计入活跃数，强制结束按钮也会错误开放；若写入 `ended`，现有终态保护无法按预期工作。
- **修订**：列出当前状态枚举及允许转换，直接沿用 `finished`，或明确新增管理终态所涉及的全部兼容改动。区分存续会话、正在执行会话和失败待恢复会话，避免用一个“活跃”指标混称。

### R08〔高〕租约恢复和强制结束不是更新几个字段

- **位置**：6.5、8.4、AD-2.2（第 294、421、469 行）。
- **证据**：现有租约依靠 `lease_owner + lease_generation + lease_until` 校验，执行由 WebSocket 调度；`_heartbeat` 持续续租，写事件前检查租约。
- **问题**：方案只验收 owner 更新和状态落库，没有定义接管后谁执行、谁续租、待执行命令如何处理，也没有阻止在途执行者继续写回。按钮禁用不能代替服务端并发校验。
- **修订**：恢复时在事务内重新检查状态与租约，递增 generation 使旧执行者失效，再通过明确执行器调度可恢复命令；明确无客户端连接时是否可恢复。强制结束须同时封闭新命令、作废租约、处理队列、发布前端可识别的终止事件；定义在途模型请求无法撤回时的成本结算及结果丢弃规则。验收应覆盖并发恢复、结束与执行竞争、旧 worker 写回被拒绝。

### R09〔高〕files 表并非上传文件登记表

- **位置**：6.6、7.2、8.5（第 301、381、426 行）。
- **证据**：`services/ppt.py:119` 将生成 PPT 登记到 `files`；`resolve_download` 从该表解析下载，包含过期和目录边界检查。
- **问题**：将 files 与 PPT 分成两个独立对象会重复计数。目录里有文件不等于存在可下载登记；“可选删除 files 记录”会留下失效记录。
- **修订**：本期将 files 作为成果登记源，目录扫描仅用于核对孤儿文件、缺失文件与临时文件。若确需上传文件管理，先补上传持久化和登记模型。PPT 删除必须定义登记及磁盘一致性，文件占用失败时不能误报成功；管理员下载通过管理鉴权后复用 `resolve_download`，不能直接跳到要求业务令牌的下载 URL。

### R10〔高〕项目与 Chroma 物理集合混为一谈

- **位置**：6.7、7.2、AD-2.3（第 310、382、470 行）。
- **证据**：`services/rag.py:29` 按 embedding 指纹命名集合，项目是 metadata 中的 `project_id`；文档管理会跨 `qc_` 集合处理，另有 `__legacy_unassigned__` 历史数据。
- **问题**：物理集合可含多个项目，一个项目也可跨多个集合。“按项目清空集合”若被实现为删除 collection，会误删其他项目。现有 `list_documents(project_id)` 还要求先知道项目 ID，不能直接产出全部项目清单。
- **修订**：页面和 API 统一为“项目知识库”，项目清空使用跨相关集合的 `project_id` 过滤；物理集合管理独立定义或移出本期。补项目发现机制、历史未归属数据展示、去重计数、分批删除、并发导入互斥及跨集合部分失败处理。验收确保其他项目不受影响，切换模型后被删除文档不会再次出现。
- **补充**：现有查询/删除会先初始化 embedding client，`core/clients.py:63` 在外部模型模式且无 Key 时拒绝初始化。运维查看及删除元数据应有不依赖模型凭据、也不触发向量生成的路径，否则模型配置故障时恰好无法维护知识库。

### R11〔高〕数据集清理范围及删除后果未闭环

- **位置**：6.4、8.3（第 284、285、416 行）。
- **证据**：`services/usage.py:142` 的 `purge_expired_entities()` 同时清理数据集和会话及事件、命令，不能无差别用作“只清数据集”的接口。
- **修订**：抽取带明确 scope 的公共清理服务；在途使用中的数据集如何删除、已启动研讨是否继续使用快照、重启或恢复是否仍依赖数据集，应逐项确定。删除不会自动清除研讨快照、向量或生成成果，页面须说明实际范围。“恢复”若指数据找回，本方案的物理删除不支持，应从目标移除或另加回收机制。
- **补充**：现有会话过期清理也没有检查活动租约。应明确执行中的过期会话是延后清理，还是先终止并结算后再删除，不能将时间到期直接等同于可以安全删除。

### R12〔高〕配置更新和令牌轮换缺少一致性与交付方案

- **位置**：6.9、6.10、8.7、12.3（第 330、337、436、574 行）。
- **证据**：`core/config.py:56` 写文件后才构造 Settings 校验；revision 是递增计数，并无请求版本冲突检查。`frontend/src/api/client.ts` 从构建变量读取业务 token；`discussion.py:24` 仅在 WS 建连时校验 token。
- **问题**：文件替换原子性不等于配置合法性、内存与文件一致性，也不解决多人页面覆盖。轮换后“旧令牌立即失效”对已连接 WS 不成立；新令牌如何安全取得、现有前端如何更新也未定义。
- **修订**：先校验候选配置，再持久化并更新依赖；添加 expected_revision/409 防覆盖，明确环境变量覆盖 `.env` 的部署处理。轮换需要近期密码确认，定义一次性安全展示、响应丢失后的恢复、前端重配或重建步骤。若要求断开旧 WS，加入连接追踪及失效机制并计入变更范围；否则限定为新 HTTP 请求和新 WS 连接失效。

## 三、功能—接口—页面—任务—验收覆盖核对

| 功能承诺 | 当前缺口 | 建议落位 |
|---|---|---|
| 系统配置管理 | 6.10 有接口，7.1 无 `/admin/config`，7.2 无配置页，路线图无明确任务。 | 若本期保留，补页面、配置字段范围、写入/冲突/重启验收，放入 P2；否则从本期范围移出。 |

## 四、建议的修订结构与实施顺序

保留现有框架，但在架构章节后新增“领域定义与操作规则”，在测试章节前新增“部署迁移与回滚”。每个功能统一按以下顺序编写，避免 API、页面和验收各说一套：

> 使用场景 → 数据来源与真实模型 → 权限 → 前置状态 → 请求与响应 → 事务/并发/重试 → 页面反馈 → 审计 → 验收。

建议阶段调整：

1. **P0：设计定稿与安全基础。** 先关闭 R01—R06、明确 R07—R12 的领域规则；完成初始化、认证、CSRF、限流分流、事务审计、迁移和浏览器联调。确定生产部署方式。
2. **P1：可信的只读后台。** 看板、用量、会话/成果/知识库的正确数据模型、系统状态、审计查询；验证脱敏、查询性能、局部失败和空库表现。
3. **P2：逐项开放管理写操作。** 每项操作同时交付事务或补偿方案、服务端状态校验、确认页面、审计和故障测试。会话恢复/终止最后开放。
4. **P3：发布收口。** 完成备份恢复演练、并发业务回归、部署文档、浏览器端到端测试及上线检查。此阶段不再补前面发布必需的基本安全能力。
5. **P4：可选分析。** 性能数据证明需要后再引入预聚合；预测与 PDF 分开评估。

原工期应视为粗估。当前缺少人员投入、可复用组件验证和风险工作量；上述状态机、迁移、配置写入及删除补偿工作应独立估算后，再给出可承诺排期。

## 五、补充发布门禁

除原测试矩阵外，至少增加以下可判断通过/失败的场景：

- **认证闭环**：首次初始化→登录→CSRF 写入→改密→重启→旧密码失效→本机恢复；后台轮询不意外无限续期；吊销其他会话不登出自己。
- **部署闭环**：同源代理或所支持的跨源配置中，Cookie 可设置、携带、读取所需 CSRF；非可信来源拒绝；直接刷新管理页正常。
- **写入闭环**：数据库锁、磁盘满、文件被占用、审计失败、Chroma 部分失败、请求响应丢失时，结果可追踪、可重试且无误报成功。
- **研讨闭环**：完成会话不计为活跃；管理员结束后旧 worker 不再写事件；租约竞争只有一个执行者；在途成本不被清理抹除。
- **删除闭环**：只清理指定对象和 scope；跨项目隔离；删除后的登记、磁盘及向量状态符合规则；模型切换不复活已删文档。
- **配置闭环**：两个页面同时提交发生明确冲突；非法设置不污染 `.env`；令牌轮换后的新请求、既有 WS、前端重新接入均符合已声明规则。
- **数据闭环**：跨日边界、零预算、未知成本、已复位预留、空桶、全量/区间统计与 CSV 一致；脱敏覆盖所有出站字段。
- **运维闭环**：旧库升级、迁移失败和备份恢复演练通过；管理查询与业务并发时达到定义的性能目标，且不造成业务明显退化。

**通过条件**：高优先级问题形成明确决策并同步到 API、模型、页面、任务和验收五处；中优先级问题有对应任务及阶段门禁。做到这一点后，方案才从功能清单转为可实施、可验证的建设计划。
